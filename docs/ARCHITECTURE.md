# Архитектура

## Границы системы

Проект разделён на HTTP-слой, управление процессом, предметную модель состояний, пул ресурсов и адаптеры. `ImportService` зависит от порта `JobStore`, а `InMemoryJobStore` и `SqlAlchemyJobStore` находятся на внешней границе.

## Resource pool

`ResourcePool[T]` хранит слоты с независимым лимитом нагрузки. Общий семафор ограничивает число операций, а `Condition` позволяет ждать освобождения занятого слота без опроса в цикле.

Необязательный `serialization_key` задаёт ещё один уровень конкурентности: операции с одним логическим каналом выполняются последовательно. Блокировка по ключу берётся до общей ёмкости пула, поэтому ожидающая операция не занимает дефицитную сессию; для других ключей параллельность сохраняется. `KeyedLockRegistry` учитывает владельцев и ожидающие задачи, корректно освобождает запись при отмене и не допускает неограниченного роста реестра.

Во время попытки pool:

1. выбирает доступный слот с наименьшей нагрузкой и числом ошибок;
2. выполняет callback под `asyncio.wait_for`;
3. при успехе сбрасывает consecutive failures;
4. классифицирует ошибку через `is_retryable`;
5. постоянную ошибку возвращает без retry, а временную добавляет в историю попыток;
6. после порога ошибок включает cooldown и переключается на следующий ресурс;
7. при исчерпании попыток возвращает структурированный список ошибок.

## State machine и recovery

```text
received → fetching → transforming → publishing → completed
               │            │             │
               └──────── needs_attention ─┘
```

Переходы проверяются таблицей `ALLOWED_TRANSITIONS`. `raw_items`, `prepared_items` и `receipts` служат checkpoint. При повторе стадия определяется по последнему заполненному checkpoint. Publication receipt хранится отдельно для каждого item, поэтому уже завершённые действия не повторяются.

`RecoveryPlan` строится внутри предметной модели, а не в HTTP-слое. Он проверяет уникальность исходных идентификаторов, соответствие подготовленных элементов исходным и отсутствие подтверждений для неизвестных элементов. Только после этой проверки сервис выбирает состояние продолжения; API показывает вычисленный план, не воспроизводя правила восстановления.

## Идемпотентность

Оба адаптера `JobStore.get_or_create` сопоставляют входной ключ одной задаче и сверяют SHA-256 fingerprint параметров запроса. В памяти это защищено `asyncio.Lock`, в БД — уникальным ограничением и обработкой конкурентного `IntegrityError`. Локальная keyed-блокировка не расходует SQL lease на конкурирующие coroutine одного процесса, а условный `UPDATE ... RETURNING` выдаёт возобновляемый lease только одному экземпляру сервиса. Адаптер назначения получает стабильный токен элемента `<job-id>:<external-id>`; его постоянное хранение на стороне назначения закрывает окно между внешним side effect и SQL-checkpoint.

`SqlAlchemyJobStore` сохраняет checkpoint после каждого перехода и publication receipt. Unique constraints на `idempotency_key` и пару `(job_id, external_id)` поддерживают тот же контракт в постоянном хранилище.

## Ошибки

После исчерпания временных сбоев `ResourcePoolExhaustedError` содержит перечень попыток. Ошибки данных не повторяются. Orchestrator переводит активную стадию в `needs_attention`, сохраняет checkpoint и позволяет безопасно вызвать `/imports/{job_id}/retry` даже после перезапуска сервиса.

## Runtime и готовность

`RuntimeSettings` валидирует лимиты пула, timeout, cooldown и `DATABASE_URL` до запуска обработки. Без URL API работает на in-memory store для локальной проверки; с `postgresql+asyncpg` подключается постоянное хранилище.

FastAPI lifespan инициализирует схему до приёма трафика и закрывает engine при shutdown. Liveness не зависит от внешних систем, readiness проверяет PostgreSQL через `SELECT 1`. Compose-граф не запускает API до `pg_isready`, а container healthcheck обращается именно к readiness-границе.
